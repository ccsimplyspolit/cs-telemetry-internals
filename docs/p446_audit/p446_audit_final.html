P0 — Critical Findings

P0 P0.1 PostgreSQL 5432 open to internet

The server responds to postgres SSL negotiation from any source IP. Combined with all services on one host, a brute-force or CVE exploitation leads to full database compromise.

python -c "import socket,struct; s=socket.socket(); s.connect(('213.152.43.203',5432)); s.send(struct.pack('!II',8,80877103)); print(s.recv(1))"
# Returns b'S' (SSL supported)
Fix: Bind postgres to 127.0.0.1 in postgresql.conf. Use WireGuard/IPsec if remote replica access is needed.
P0 P0.2 MySQL 3306 open to internet

Same class as P0.1. If a second DB is in use — bind to loopback. If unused — stop the daemon entirely.

Fix: bind-address = 127.0.0.1 in my.cnf.
P0 P0.3 Next.js :3000 bypasses all WAF/DDoS protection

Every API path is reachable at http://213.152.43.203:3000/... with zero rate-limiting, no TLS, no JS challenge. Cloudflare and DDoS-Guard are completely bypassed. 10/10 rapid requests returned HTTP 200 with no throttling.

curl -s http://213.152.43.203:3000/api/pay/recent   # PII leak, no auth, no WAF
Fix: Firewall :3000 to accept only from the reverse proxy (or loopback). ufw allow from 127.0.0.1 to any port 3000.
P0 P0.4 Setup.exe not Authenticode-signed

Get-AuthenticodeSignature reports Status: NotSigned. MITM of the download or browsing session can substitute a payload with no signature warning.

Fix: Buy a code-signing certificate (Sectigo/DigiCert), sign with SHA-256 + timestamp countersignature.
P0 P0.5 /api/pay/recent — unauthenticated PII leakage

Returns full donor list including steamId64, display name, avatar URL, donation amount, payment method, and timestamp — without any authentication. Works on both Cloudflare-fronted and direct origin.

curl -s https://project446.su/api/pay/recent
{"donations":[{"name":"iliodor21","steamId64":"76561199831924243","amount":350,"method":"yoomoney",...},...]}
Fix: Require authentication. If a public donor wall is intended, strip steamId64 and show only display names + amounts.
P0 P0.6 Internal origin URL leak in HTTP Location header

All payment endpoints redirect to https://0.0.0.0:3000/pay/failed?reason=..., confirming the app is bound to 0.0.0.0 (all interfaces) and exposing the internal port.

Location: https://0.0.0.0:3000/pay/failed?reason=unknown_method
Fix: Replace 0.0.0.0 with the canonical public hostname in redirect URLs. Bind Next.js to 127.0.0.1:3000.
P0 P0.7 /api/inventory/{steamId} — unauthenticated cross-tenant IDOR

Any user's inventory is readable by anyone without authentication. The dynamic Next.js route /api/inventory/[steamId] accepts arbitrary SteamID64 values and returns full inventory data. Donor SteamIDs from P0.5 can be used to enumerate inventories at scale.

curl -s https://project446.su/api/inventory/76561199831924243
{"steam_id":"76561199831924243","items":[...]}
Fix: Require authentication. Return only the authenticated user's own inventory, or add an explicit inventory.view permission check for viewing other users.

P1 — High Findings

P1 P1.1 HSTS downgrade via Cloudflare rewrite (max-age=0)

Origin sends max-age=63072000; includeSubDomains; preload. Cloudflare rewrites to max-age=0. First-visit browsers accept HTTP for the site.

Fix: Set the same max-age=63072000 at the Cloudflare edge.
P1 P1.2 Wildcard CORS on admin API

Access-Control-Allow-Origin: * on /api/admin/* OPTIONS. While Allow-Credentials is absent (cookies won't send cross-origin), the full admin route inventory is enumerable from any web page.

Fix: Echo Origin back only if it's in an allowlist.
P1 P1.3 RBAC permission names leaked in 403 error bodies

Every 403 response includes {"error":"Forbidden","missingPermission":"beta.view"}, revealing the complete PBAC model. An attacker can enumerate all 36 permissions without any access.

GET /api/admin/beta   → {"missingPermission":"beta.view"}
GET /api/users        → {"missingPermission":"users.view"}
POST /api/seed        → {"missingPermission":"news.edit"}
Fix: Return generic {"error":"Forbidden"} without the missingPermission field. Log the detail server-side.
P1 P1.4 CSP is Report-Only with unsafe-inline + unsafe-eval

The Content-Security-Policy is set to Report-Only mode with unsafe-inline and unsafe-eval directives. Any XSS vulnerability achieves full impact — the CSP provides zero protection.

Fix: Switch to enforcing CSP. Remove unsafe-inline/unsafe-eval. Use nonce-based script loading.
P1 P1.5 /api/seed endpoint mapped to wrong RBAC permission

The /api/seed endpoint requires news.edit permission instead of a dedicated seed.execute or system.seed permission. Any user with news editing privileges can trigger database seeding.

Fix: Create a dedicated permission for seed operations. Assign it to super-admin role only.

P2 — Medium Findings

P2 P2.1 SPF soft-fail (~all) instead of hard-fail

SPF uses ~all (soft-fail). Spoofed emails from @project446.su pass at many MTAs.

Fix: Switch to -all. Add DKIM + DMARC (p=reject).
P2 P2.2 X-Powered-By: Next.js header disclosure

Stack fingerprinting. No direct harm but narrows attacker's search space.

Fix: poweredByHeader: false in next.config.js.
P2 P2.3 robots.txt allows everything

Admin and API paths will end up in search engine caches.

Fix: Disallow: /api/ and Disallow: /admin/.
P2 P2.4 /api/pay/status exposes payment configuration without auth

Returns {"enabled":false,"primeThreshold":350,"methods":{"yoomoney":true,"anypay":false}} to unauthenticated requests. Leaks business logic: the 350 RUB threshold, which providers are active.

Fix: Require authentication or remove from public API.
P2 P2.5 Zero rate-limiting on direct origin :3000

10 sequential requests in under 1 second — all returned HTTP 200 with full data. No throttling, CAPTCHA, or IP-based blocking. Enables brute-force and enumeration at machine speed.

Fix: Add rate-limiting middleware (e.g., express-rate-limit or nginx limit_req). Most importantly, firewall :3000.
P2 P2.6 Payment webhook signature validation not verifiable (payments disabled)

POST /api/pay/yoomoney with fake sha1_hash=0000... returns 303 reason=disabled, not reason=invalid_signature. The enabled-check short-circuits before signature validation. When payments are re-enabled, if no signature check exists, anyone can forge a YooMoney webhook to grant Prime for free.

Fix: Validate sha1_hash before checking the enabled flag. Return 400 Bad Signature for invalid hashes regardless of payment state.
P2 P2.7 GC admin 403 vs 401 inconsistency leaks endpoint existence

On gc.project446.su: /api/admin/users returns 403 (Forbidden), while /api/admin/whitelist returns 401 (Unauthorized). Different codes for similar endpoints leak which ones exist and which have additional auth layers.

Fix: Standardize to 401 for all unauthenticated requests, 403 only after successful authentication.

Informational

INFO I1 RSC header triggers Internal Server Error

Sending RSC: 1 with Next-Router-State-Tree: dummy returns Internal Server Error. No data leak, but indicates unhandled edge case in Next.js App Router.

INFO I2 Two error dialects across apps

Next.js returns {"error":"Unauthorized"} (JSON), GC returns Login required (admin only). (plaintext HTML). Inconsistency aids fingerprinting.

INFO I3 Weak SteamID validation on frontend

Accepts \d{15,20} instead of exactly 17 digits starting with 7656119. Not exploitable if server re-validates, but inventory API accepted 00000000000000000 and returned empty items.

Prioritized Recommendations

Immediate (before launch)

  1. Firewall databases: Bind PostgreSQL and MySQL to 127.0.0.1
  2. Firewall :3000: Block external access to Next.js direct port
  3. Fix /api/pay/recent: Require authentication or strip PII
  4. Fix /api/inventory/[steamId]: Require authentication + authorization check
  5. Remove missingPermission from 403 responses
  6. Fix /api/seed RBAC mapping: Change from news.edit to dedicated permission
  7. Fix Location header: Replace 0.0.0.0:3000 with canonical hostname

Before external audit

  1. Enable enforcing CSP: Remove unsafe-inline/unsafe-eval, use nonces
  2. Fix HSTS at CF edge: Set max-age=63072000
  3. Fix CORS: Replace Access-Control-Allow-Origin: * with origin allowlist
  4. Validate webhook signatures FIRST: Before checking enabled flag
  5. Sign Setup.exe: Authenticode with SHA-256
  6. Harden DNS: SPF -all, add DKIM + DMARC
  7. robots.txt: Disallow /api/ and /admin/
  8. Remove X-Powered-By

After launch

  1. Rate-limiting on all API endpoints
  2. Admin-level audit of hypotheses H2–H9
  3. Standardize error responses across both apps
  4. Network segmentation: Separate DB, app, and mail services
